§2

Session History — the append-only ledger

Q1 — How do agents manage session history?

History is not a chat log in RAM. It is an append-only ledger of immutable entries in SQLite, one database per container on the /data volume. Entries are never edited — corrections are new records. Everything the model said, every tool result, every prompt change: committed, atomically, forever.

DOCUMENTS — typed JSON state committed next to the transcript, in the same atomic commit. The ledger is what the model said; the documents are what the system knows.
SAME DB, ALWAYS — pause, crash, docker compose restart: root() reopens conversation #1 with every entry intact.
One container = one ledger. The three agents never share history: agent-a's past is invisible to agent-b. Forks and subagent children get their own ledgers.

Mechanism A — the atomic commit

commit( tx ) tx.entry… tx.entry… ALL OR NOTHING

A commit appends entries, edits documents, creates tasks — together. A crash mid-commit leaves the store exactly as before. No half-written thoughts, ever.

Mechanism B — requestId deduplication

POST requestId: demo-1 ✕ connection drops
retry requestId: demo-1 same submission returned

Submitting the same requestId — even after a restart — returns the already-admitted Submission instead of running twice. Retries are free; side effects happen once.

§3

The Context Window — derived, never stored

Q2 — How does history reach the window? What is appended per interaction, and what controls it?

The trick: nothing is “appended to the window” incrementally. Before every model request, the window is derived from committed entries — from the newest head marker to the tail. A head marker is the newest pi.reset or pi.compaction: a boundary the model cannot see across.

H.head — the marker points at the first kept entry (#13). The visible range is exactly H.head … tail. Edits inside the range: the newest edit wins.
WINDOW = DERIVED VIEW — entries → messages, assembled fresh before each request. It is a projection of the ledger, never a stored blob.
NO ORPHANS — a tool call whose result never arrived (history cut before it) is settled as “Tool result unavailable”.
Two O(1) reads find the tail and the newest head marker — then only the range between them is scanned. This is the logical mechanism that controls what the model sees.

§4

Session Lifecycle — sleep when idle, wake when called

Q3 — How does the system manage the session lifecycle?

The agent is a two-state machine: PAUSED ⇄ ACTIVE. Closing means checkpointing and closing the SQLite file. Activating means reopening it and resuming whatever run the last process left unfinished. The transition triggers are requests and a timer — nothing else.

→ #pause(): checkpoint + close SQLite · POST /pause answers 409 if busy
Careful design: GET /health and GET /status are deliberately not activating — a Docker health probe every 5 s would otherwise keep the agent awake forever.

The agent config is stored with the session; the deployment follows the configured model on reopen — no history wipe.

§5

Protocol — synchronous HTTP, durable semantics

Q4 — How do agents and external clients communicate? Sync or async? Concurrency?

External protocol: plain HTTP/1.1 + JSON, request/response, fully synchronous. Caddy is the only door. POST /prompt holds the connection open until the answer is committed. There is no webhook and no push channel here — instead, durability replaces async messaging: idempotent requestIds make retries safe.

PARALLELISM — read ops (/files, /file) run truly concurrently; tool calls within one round run in parallel; the three agents are fully independent (separate sessions, separate DBs).
A conversation is busy while a run works. Concurrent prompts are admitted concurrently (inFlight counts them) but executed as serialized runs by the durable inbox — order preserved, nothing dropped, even across a restart mid-queue.
§6

Summary — the four answers, distilled

Q1 · History

An append-only ledger of immutable entries in SQLite on the /data volume — one per container. Atomic commits, typed documents beside the transcript, requestId dedup, identical after pause or restart.

Q2 · Context window

Derived, never stored: before each request, entries from the newest head marker (reset/compaction) to the tail are turned into messages — incrementally, with only changed system sections re-sent. Overflow is handled by compaction thresholds.

Q3 · Lifecycle

Two states, PAUSED ⇄ ACTIVE. Requests activate (reopen + resume unfinished runs); a 5 s idle timer pauses (checkpoint + close SQLite). Open/pause serialized on one chain; probes never wake the agent.

Q4 · Protocol

Synchronous HTTP/JSON through Caddy, the only door. Concurrent prompts are queued by the durable inbox and run one at a time; reads and agents run in parallel. Durability + requestId idempotency replace async messaging.
