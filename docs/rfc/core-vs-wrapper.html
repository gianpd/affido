affido · core vs container wrapper · lifecycle derivation

One lifecycle is terminal.
The other is a loop.

The core Harness opens once and closes at shutdown. The container DurableHarness wraps that terminal lifecycle in a restart loop. Both need the same thing — a mutex that keeps two lifecycle transitions from interleaving — but they need it at different levels. This page derives why.

CORE — pi-durable Harness WRAPPER — container DurableHarness mutex — the promise-tail lock
Premise

The durability rule forces ordering.

Everything below follows from one design decision in pi-durable: a change is committed to Storage before it is shown. Conversations, model turns, tool calls, documents — all of it lands on a single atomic line.

Harness.open(storage, options, context) opens one Session over one Storage backend.

The Session holds one mutation line — a promise tail. Every commit and every multi-read is a job appended to it, so at most one transaction is in flight at any moment.

Durability is the storage backend's job: SQLite runs journal_mode = WAL with synchronous = NORMAL, so a crashed process recovers the last committed transaction from the write-ahead log. On reopen SQLite rebuilds the file from the WAL; the Harness then does logical recovery — it flips running tasks back to pending.

Ordering is the line's job: it makes “the last committed record” a single, atomic, totally-ordered step. The WAL makes the last commit survive; the line makes it well-defined. Both are needed — and with synchronous = NORMAL, only process crashes are guaranteed: a power or host failure may lose the newest commit.

Step 1 — derive each lifecycle from first principles

Follow the causes down to the conclusion.

Left and right share the same first cause. They diverge at the third conclusion: what does "stop using the storage" mean?

CORE — Harness @earendil-works/pi-durable
01
Cause

A committed change is atomic and totally ordered: it is shown only after it is stored, and never applied halfway.

▼ therefore Effect

All writes funnel through one Session mutation line — a promise tail that runs one job at a time. (The storage's WAL supplies the durability; the line supplies the order.)

02
Cause

A crash can leave tasks in a running state that no process is executing.

▼ therefore Effect

open() reconciles running → pending but dispatches nothing. Recovery is prepared, not started.

03
Cause

Nothing may run before the host has installed extensions or seeded state.

▼ therefore Effect

A freshly opened Harness is paused: the scheduler's #enabled is false, reported as scheduling: "paused".

04
Cause

Paused work must eventually run, but exactly once and only when asked.

▼ therefore Effect

resume() flips #enabled = true. It is idempotent and one-way — there is no public pause(). Progress calls (submit, waitForIdle…) auto-resume.

05
Cause

The only way to release Storage is to close the Harness.

▼ therefore Conclusion

close() seals admission, aborts and joins invocations, then closes Storage. It is terminal: the one-shot promise is reused, and after it resume() throws.

⊕
Derived lifecycle

open → paused → resume → running → close → closed (terminal)

One open per process lifetime. No back-edge.

WRAPPER — DurableHarness affido
01
Cause

A long-lived HTTP container is idle most of the time, but the core holds the SQLite file open and the process busy.

▼ therefore Effect

The container wants to release storage when idle and reclaim it on the next request.

02
Cause

From the core derivation: the only way to release storage is close(), and close is terminal.

▼ therefore Effect

The wrapper cannot pause the core. It must close it and build a new one on the next request. Its "pause" is literally #runtime.close().

03
Cause

Releasing and reclaiming storage means the lifecycle now has a back-edge.

▼ therefore Conclusion

The wrapper runs the core's open→resume→close many times, one cycle per idle/request period. The terminal lifecycle becomes a loop.

04
Cause

Two independent actors now drive that loop: an idle timer and an HTTP request.

▼ therefore Effect

They can fire at the same moment — a timer closing as a request opens. Without a guard, storage is torn out from under a live conversation.

05
Cause

The core's mutation line lives inside one Session and dies when that Session closes. A new open gets a brand-new tail.

▼ therefore Effect

The core cannot serialize the wrapper's open/close cycle. The mutex must move one level up.

⊕
Derived lifecycle

idle → activate → open + resume → running → idle/close → idle

A cycle, guarded by the wrapper's own promise-tail mutex.

The pivot: the core serializes operations inside a Harness; the wrapper serializes the Harness's own open/close cycle.
Step 2 — the lifecycles, drawn

Same boxes. One missing arrow.

The wrapper's back-edge is the whole difference. Everything else follows from it.

No back-edge. Once closed, the Harness is done. Reopen means constructing an entirely new Session with a new mutation line. The core's lifecycle diagram is a straight line by design.

Wrapper lifecycle — agent/harness.ts

The dangerous edge. The idle timer and an incoming request can both want to cross the open↔close edge. The wrapper's #serialize mutex stands exactly on this edge so only one transition runs at a time.
Step 3 — the same lock, one level up

The wrapper's mutex is a copy of the core's.

Recognising this is the punchline: #serialize is not a new invention. It is the Session's mutation line reimplemented around the Harness instead of inside it.

● CORE — session.ts #enqueue
// one promise tail: the Session's mutation line
#enqueue<T>(job: () => Promise<T>): Promise<T> {
  const run = this.#tail.then(job);
  this.#tail = run.then(
    () => undefined,
    () => undefined,
  );
  return run;
}
Serializes commits and multi-reads inside one open Session. Each Harness.open() gets a fresh #tail.
● WRAPPER — agent/harness.ts #serialize
// Serialize open/close so a timer and a request never interleave.
#serialize(task: () => Promise<void>): Promise<void> {
  const next = this.#chain.then(task, task);
  this.#chain = next.then(
    () => undefined,
    () => undefined,
  );
  return next;
}
Serializes the Harness's own open/close cycles. #chain survives across close/reopen, so it can guard them.
Only one real difference. The core passes a single handler (#tail.then(job)) because #tail is always the swallowed, never-rejecting version. The wrapper passes task twice — a redundant but harmless belt-and-suspenders. The mechanics are identical: append to a tail, swallow the settled state, return the real promise to the caller.

Conclusion

The core pays for durability with a terminal lifecycle. The wrapper pays for idleness by looping that lifecycle — and looping it is exactly what makes the second mutex necessary.

Because the core can only release storage by closing, the wrapper must close and reopen. Because it reopens repeatedly, two actors race on the open/close edge. And because the core's mutation line dies with each close, that race cannot be fixed down there — so the same promise-tail pattern is lifted one level up into DurableHarness#serialize. One concept, two altitudes: order inside the Harness, and order around the Harness.
