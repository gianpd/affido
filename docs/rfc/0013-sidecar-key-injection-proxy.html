01

The change is one hop, in one direction

Delivery target moves; desired state, ciphertext and isolation do not

Under RFC 0012 the manager hands {provider, modelId, apiKey} to the agent, and the agent process holds the key in an InMemoryCredentialStore. Bash and every other tool run as children of that process, in that container. Under RFC 0013 the same ciphertext is decrypted at the same moment, but the plaintext is delivered to a second container — and the agent gets a keyless payload plus a baseUrl that points at it.

Same inputs, same serialization, same OLTP rows. One payload is split in two, and only one half contains a secret.

before · RFC 0012

The key is plaintext in the attacked process

The honest guarantee was: not persisted anywhere, plaintext exactly in the process that must use it. A prompt-injected document can direct bash at /proc/<server>/mem and the architecture does not forbid it.

after · RFC 0013

The key is plaintext in a process the agent cannot read

Full compromise of the agent — model, tools, node_modules, the server process itself — finds no key material in the container, and the sidecar forwards only to the host pinned at delivery time.

what stays true

Abuse was always possible, and still is

An agent that must call the provider can spend quota. The threat boundary moves from disclosure or abuse to abuse only; spend limits and key rotation stay the mitigations.

Phase 0 is independent. A seccomp deny-list (ptrace, process_vm_readv/writev, pidfd_getfd, kcmp) plus --ulimit core=0 on both containers lands first and hardens today's RFC 0012 delivery without waiting for the sidecar. Both are drawn on the agent box below because they ship with it.

03

One proxied call, header by header

The sidecar is a wire-level pass-through: it needs no pi-ai change, only a rewritten baseUrl

The whole mechanism is one fact from pi-ai: every supported API layer builds the upstream URL from model.baseUrl. Register the model with the sidecar's URL instead of the vendor's and all traffic routes through the sidecar. What the sidecar must do is narrow — strip, stamp, pin, relay.

agent → sidecar
POST /deepseek/chat/completions Host: sidecar:8081 Authorization: Bearer sk-sidecar-… Content-Type: application/json { "model": "deepseek-chat", "stream": true, … } // placeholder only, no secret
sidecar → upstream
POST /chat/completions Host: api.deepseek.com Authorization: Bearer <the user's key> Content-Type: application/json { "model": "deepseek-chat", "stream": true, … } // pinned, TLS verified, body untouched
sidecar → refused
POST /attacker.example/collect Host: sidecar:8081 Authorization: … 403 unpinned host // no agent header, path or model // field can redirect the key

Two behaviours travel with this rewrite, both acceptable in phase 1. Prompt caching: pi-ai emits prompt_cache_key only when the baseUrl contains api.openai.com, so a proxied OpenAI prompt loses server-side caching while cacheRetention is off — the sidecar could add the header itself later, since it knows the real host. Custom-endpoint quirks: compat is resolved from the real baseUrl before the rewrite, so auto-detection never sees the sidecar URL.

removed by this RFC

Agent RAM for the entire key lifetime

The largest window in RFC 0012 disappears: not shortened, removed. docker exec into the agent container, its environment, its filesystem and its process memory are all out of reach of the key by construction, not by hardening.

added by this RFC

One more process, one key, one network

A per-sandbox sidecar holds exactly one tenant's key. Reaching it means breaking the per-user --internal isolation that already separates tenants — the wall e2e-test/security.sh proves, now with one more target to probe.

Why never the manager itself: routing tenant LLM traffic through one process would put every tenant's plaintext in one place, inverting the per-user isolation the stack is built on, and would make the control plane a data-plane bottleneck. The invariant is one key per process, not one sidecar per user.

05

Lifecycle: the pair, or nothing

Every operation that used to act on one container now acts on two

Resolve — every prompt pays for correctness, not for state

serialized on the /prompt chain
  1. 1
    Ensure the pair existscreate_args → agent + sidecar

    Agent with AGENT_MEMORY/AGENT_CPUS, sidecar with SIDECAR_MEMORY=128m/SIDECAR_CPUS=0.25. Same --internal network, no volumes, no published ports.

    both created
  2. 2
    Wait for bothwait_healthy ×2

    A dead sidecar fails the resolve with sidecar_unhealthy, exactly as an unreachable host fails with egress_blocked. No silent faux fallback.

    fail closed
  3. 3
    Deliver the key halfPOST /config → sidecar

    {provider, modelId, apiKey, baseUrl?}. One call pins the upstream and installs the key atomically: in-flight requests finish on the old upstream, queued prompts use the new one.

    key resident
  4. 4
    Deliver the keyless halfPOST /config → agent

    {provider, modelId, viaSidecar: true}. buildProvider resolves compat from the real URL, rewrites every model baseUrl to the sidecar, registers the placeholder credential.

    ready
Idle pause still costs nothing. /health and /status never open storage and never activate the harness, so an idle user keeps zero active containers — the sidecar is evicted with the agent, not left running.

Reconcile, restart, switch

desired state lives in the OLTP
  1. 1
    Sidecar restarted or evicted while idlekey lost from memory

    The next resolve re-delivers from the OLTP ciphertext. Nothing is persisted in the sidecar, so nothing can be stale; in-flight streams fail as a provider 5xx would today.

    re-deliver
  2. 2
    User switches provider or keyone /config, one lock

    Key and pinned upstream are replaced together in a single delivery, then the agent is re-configured. The session survives: RFC 0012 R8 is untouched.

    atomic swap
  3. 3
    docker rm of either containerone event, not two

    The watchdog re-provisions the pair. An agent without its sidecar is an incomplete sandbox, never a working one.

    pair recreated
  4. 4
    Faux provider selectedno key, no hop

    The sidecar accepts and ignores the config; the agent stays in direct mode and never proxies. The keyless default and verify.sh behave exactly as today.

    unchanged
Egress is still network-wide in phase 1. When a real provider is selected the whole per-user network opens, as before. Narrowing NAT to the sidecar only is phase 2, worth doing only if content exfiltration — already possible and accepted — enters the threat model.
06

Why every catalog provider still works

Verified against pi-ai 1.3.0: all four wire APIs read model.baseUrl

The design would be dead if any provider constrained its base URL. None does: every API layer builds the upstream from model.baseUrl, and the two provider-specific branches check the provider id before the baseUrl. So the rewrite is one field of plain model data, at registration time, with no fork and no wrapper.

The e2e fake upstream is exactly the custom-endpoint case, which is what makes the whole chain testable keylessly: browser → manager → OLTP → sidecar → fake upstream, with an assertion that the key appears in no agent response and no log along the way.

07

What the promoted model must keep true

If a later change breaks one of these, the diagram is wrong, not the requirement
R1 · agent never holds the key
No plaintext in agent memory, env, disk or API responses. docker exec into the agent is not enough to recover it.
R2 · the agent can still call the provider
Streaming, usage, tool calls and thinking levels work unchanged; the sidecar is a wire-level pass-through.
R3 · upstream pinning
One host, fixed at delivery. No agent-supplied URL, header or parameter redirects the key.
R4 · RFC 0012 flows keep their shape
Setup, validation, catalog, per-user isolation, idempotent resolve and session survival across provider switches.
R5 · topology stays manager-owned
The sidecar is created by create_args, never in compose; run.sh fails on sidecar* just as it fails on agent*.
R6 · no new published ports
Internal network only, like the agent's :8080 today.
R7 · lifecycle is a pair
Evict, pause, recreate together. A resolve never routes an agent to a dead sidecar.
R8 · tests stay keyless
The faux path is untouched; BYOK is proven against the fake upstream registered as a custom endpoint.
R9 · abuse stays visible
Provider and model remain identifiable in prompts, usage events and traces, via the sidecar /status fingerprint.
R10 · the sidecar gets its own caps
128 MiB / 0.25 CPU, env-tunable; never the agent's 512 MiB / 1.0. Per-user ceiling 640 MiB + 1.25 CPU, not double.
does not change

Everything outside the delivery hop

Caddyfile, frontend, the OLTP schema, the /providers/* surface, validation, catalog generation, the verify.sh shape, the faux provider and the keyless default. This is a manager, agent and e2e change; the image stays one deploy unit with two entrypoints.

still out of scope

Host and control-plane compromise

Root on the host, or on the Docker daemon, still reads every key. TEEs are rejected as operational cost with no effect on abuse. Traffic analysis — that a provider call happened — is accepted. The sidecar moves one boundary, not all of them.
